# Contributing to verge

The Escapement Project's [contribution guide](https://github.com/Escapement-Project/.github/blob/main/CONTRIBUTING.md)
applies here: issues, pull requests, commit messages, vendor firmware and the use of LLMs. This
file adds what is particular to verge: how it is built and how to test it.

## How it is built

`verge-probe` owns discovery, update paths, bootloader operations, image parsing, releases and
batch updates. It also exposes Verge's debug and bridge features through probe-rs. This repository
contains the `cli` and `gui` frontends. The GUI uses egui and runs USB work on a worker thread.
A separate thread blinks finished probes during batch updates.

`verge-probe` talks to the ROM bootloader through `rblhost`, NXP's own Rust client, the version
LinkServer ships. Its default USB transport opens the first matching bootloader, so `verge-probe`
supplies a `hidapi` transport that opens the selected one.

The GUI takes its colours, type and icon from the Escapement Project's design tokens:
`gui/src/tokens.rs`, the fonts in `gui/fonts/` and the icons in `gui/icons/` are copies of files
the project's site repository generates. The fonts are Saira, Hanken Grotesk and Martian Mono,
under the SIL Open Font License. `gui/fonts/README.md` records their roles and licences, and how
to check the copies against the site's build. The window shows the day or the night face as the
system prefers, and follows a change while it runs. On Linux, where winit reports no preference,
it reads the desktop's colour-scheme setting through the XDG portal with `dark-light`; without a
portal it shows night.

Verge's mark moves in two places: once at launch in the window's top strip, and in a loop above
"Nothing" and "Plug in an MCU-Link" while nothing is attached. `gui/src/mark.rs` only draws it:
its timing, shape and lines are `gui/src/tokens.rs`'s `mark` module, generated from the site's
design tokens and marks with the landing page's, so the two cannot drift apart. The window follows
the desktop's reduced-motion setting while it runs: the XDG portal's on Linux, the animation
effects setting on Windows and "Reduce motion" on macOS. While the desktop asks for reduced motion,
the mark holds still and egui's own animations finish at once. The tests hold it still, so their
pictures do not depend on when they are taken.

## Testing

```
cargo test --workspace
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo clippy --workspace -- -D warnings
cargo fmt -- --check
```

`.github/workflows/check.yml` runs these on every push and pull request. It also checks that a
release build leaves the simulator out, validates the desktop entry, and runs the Windows check
below.

Tests use `verge-probe`'s simulator without opening USB devices. It models recorded probe
identities, bootloader flash behaviour and GitHub responses. Simulated time advances when the
tool waits, so timeout tests run without real delays. Simulated probes can connect and disconnect
on a schedule.

The simulator, and the `minisign` crate it signs its releases with, are built only with the
`simulate` feature. The tests turn it on themselves, so `cargo test` needs nothing more. A
release build leaves it out, along with the hidden `--simulate` option.

The simulated GitHub signs releases with a key pair generated by the `minisign` crate at startup.
The tool trusts that key in place of `RELEASE_KEY`. No secret key is stored. A separate test
verifies a signature made by the minisign CLI, taken from `minisign-verify`'s documentation.

Use `--simulate` to run the CLI against the same simulator. Simulated releases are not cached,
because each run generates a new signing key, so every download needs confirmation.
`verge read` drives real probes through probe-rs, which the simulator does not model, so it
refuses under `--simulate`:

```
cargo run -p escapement-verge --features simulate -- --simulate bench
cargo run -p escapement-verge --features simulate -- --simulate stock update --yes
cargo run -p escapement-verge --features simulate -- --simulate arrivals batch --yes --count 3
```

The scenarios are `bench`, `ours`, `stock`, `stock-old`, `stock-hid`, `daplink-rs`, `isp`,
`isp-jumper`, `two-isp`, `ours-beside-isp`, `isp-ours`, `two-isp-ours`, `mini`, `isp-mini`, `busy`,
`arrivals`, `pro`, `ours-pro`, `ours-pro-old-aux`, `ours-pro-edge-loss`, `ours-pro-j15`,
`ours-pro-debugger`, `ours-pro-aux-taken`, `ours-pro-energy`, `ours-pro-energy-failed`,
`ours-pro-and-plain`, `ours-pro-held`, `ours-pro-unfitted`, `ours-pro-unfitted-j15`, `ours-plain`,
`ours-plain-marked`, `ours-plain-busy`, `ours-plain-edge-loss`, `pro-old`, `fails-writes`,
`unnamed-board`, `swd-jumper`, `pro-swd-jumper`, `stock-swd-jumper` and `denied`. Some of them:

- `arrivals`: five probes are plugged in over the first eight seconds.
- `pro`: the one probe is an MCU-Link Pro.
- `pro-old`: a Pro on NXP's firmware V3.108, which needs the jumper.
- `ours-pro-energy`: a Pro running Verge has its target supply on and has captured for 10 s. Its
  target sleeps at 20 µA and wakes at 5 mA for 10 ms in every 100 ms.
- `ours-pro-energy-failed`: that capture has stopped with an acquisition fault.
- `ours-pro-debugger`: another program holds a Pro's CMSIS-DAP interface, as a debugger would.
- `ours-pro-aux-taken`: another program holds its Verge Aux.
- `fails-writes`: the bootloader refuses every write.
- `unnamed-board`: the probe's product string names no board.
- `swd-jumper` and `pro-swd-jumper`: a standalone MCU-Link and a Pro run Verge with the SWD jumper
  fitted.
- `stock-swd-jumper`: a standalone MCU-Link runs NXP's firmware with it.
- `denied`: the system does not let this user open the one probe, which runs Verge, as Linux does
  without the udev rules.

A simulated probe boots only the simulator's own images. A real image flashed there, such as NXP's
firmware from your LinkServer install, leaves the probe silent.

GUI tests run headlessly through `egui_kittest` against the same simulator. A separate test
renders each state to PNG, in the day face and the night face, and requires a GPU:

```
VERGE_GUI_SHOTS=/tmp/shots cargo test -p escapement-verge-gui pictures -- --ignored
```

`cargo run -p escapement-verge-gui --features simulate -- --simulate bench` opens the window on the
simulated bench, labelled as such.

Two tests read real images and are skipped by default:

```
VERGE_FIRMWARE_ELF=<firmware checkout>/build/mculink_cjtag.elf \
VERGE_STOCK_S19=<LinkServer>/MCU-LINK/probe_firmware/MCU-LINK_CMSIS-DAP_V3_172.s19 \
    cargo test --manifest-path ../verge-probe/Cargo.toml --test image -- --ignored
```

They compare the image reader's output with `arm-none-eabi-objcopy` for the same files.

The Windows build is checked by compiling it, not by running it:

```
cargo check --workspace --all-targets --all-features --target x86_64-pc-windows-gnu
```
